# 0057. Rationale: store listing copy and app icon

## Context

Cocktailist is close to its first App Store and Google Play submission (specs 0037 and 0040 set the brand, bundle ID, and EAS profiles). Two store facing pieces are still placeholders. There is no listing copy in any language, even though specs 0045, 0046, and 0050 promised Portuguese, French, and Japanese listings and spec 0052 added Simplified Chinese. The app icon is the small flat coupe glass from the web logo, scaled onto a charcoal square. Spec 0037 deliberately dropped the iOS Icon Composer `.icon` until a designed icon existed.

The forces: the engineer works on Windows, and Icon Composer only runs on macOS. Store limits are strict and differ by store and field (30 characters for names and subtitles, 100 for App Store keywords, 80 for Play's short description, 4000 for descriptions, 500 for Play release notes). Store search weighs the title most, so the copy decides discoverability, and terms differ by market, so literal translation underperforms. The app is in an alcohol category, so the listing must sit well with age rating review. The team is one engineer plus AI help, with no designer, no ASO (app store optimization) tooling budget, and a preference for repo owned, tested artifacts over console only state.

Without a decision, listings get written ad hoc in two consoles, drift between locales, and break limits at submission time. The icon stays a favicon blown up to 1024 pixels on the most visible surface the app has.

## Options considered

### Copy, Option 1: Typed repo source, length test, EAS Metadata for the App Store, Play by hand

One TypeScript module per locale exports a typed listing. A vitest test checks limits and rules. A script generates EAS Metadata's `store.config.json`, and `eas metadata:push` sends the App Store copy. Play's three text fields are pasted from a generated markdown file.

**Pros**: type checked, limits enforced in CI, uses the EAS tooling already in the project, no new toolchain, comments carry translator notes.
**Cons**: Play stays manual, because EAS Metadata does not cover it, and console edits can drift from the repo.

### Copy, Option 2: fastlane deliver and supply

fastlane's metadata folders drive both stores automatically.

**Pros**: full automation for both stores, a mature and widely used tool.
**Cons**: a Ruby toolchain on Windows, a Play service account to manage, and a second release tool beside EAS, for six locales of mostly static copy.

### Copy, Option 3: Markdown docs pasted by hand

**Pros**: the simplest possible setup, readable by anyone.
**Cons**: limits are checked by eye, nothing is typed or tested, and both consoles drift freely.

### Icon, Option 1: Drawn here as a layered SVG, `.icon` generated by `pnpm icons`

Refine the existing coupe into named layer groups in `mark.svg`, keep a simplified `mark-small.svg` for small sizes, and extend the existing generator to write the `.icon` bundle that EAS's Mac builders compile.

**Pros**: keeps spec 0037's one source pipeline, free, reviewable as code, no Mac needed, and continuity with the web logo and splash.
**Cons**: no illustrator polish, and it relies on an undocumented `icon.json` format.

### Icon, Option 2: Commission a designer, build the `.icon` on a rented Mac

**Pros**: the best polish, and the real Icon Composer tool.
**Cons**: cost and lead time, plus a manual Mac step every time the icon changes.

### Icon, Option 3: Flat redesigned PNG only

**Pros**: no format risk. iOS 26 still applies its automatic treatment to flat icons.
**Cons**: gives up layered depth on iOS, and fails feature 60's Done when, which names the `.icon`.

## Rationale

For the copy, the deciding forces are strict limits and drift. A typed module plus a test turns "over the limit at submission" into a failing test today, and EAS Metadata reuses tooling the project already runs (spec 0040) rather than adding fastlane's Ruby stack on Windows for a job this small. Play's lack of EAS support is a real cost, but three fields across six locales pasted from a generated file is minutes of work per release. fastlane remains the upgrade path if Play edits become frequent.

Positioning leads with "make drinks from what you already have" because it is the one thing the app does that a plain recipe catalog does not, and it still carries the high volume "cocktail recipes" terms in the title. Keywords come from knowledge rather than a paid tool, because there is no install data yet to justify the cost; a post launch review with real store analytics is the cheaper way to tune them. Native rewrites with the app's own messages files as the glossary keep listing terms identical to what users see in the app. A second model review of Japanese and Chinese repeats what caught real problems in specs 0050 and 0052.

For the icon, the deciding forces are the Windows constraint and spec 0037's one source pipeline. Generating the `.icon` from named SVG groups keeps "edit one file, run one command" true for iOS too, and moves the macOS dependency onto EAS's builders, which already run Xcode. The undocumented `icon.json` is the honest risk; it is contained because the first device build proves it, and the fallback (a flat PNG) is still produced. Splitting detailed and small marks follows standard icon practice: a garnish that reads at 1024 pixels turns to noise at 16, and the web header logo needs the simple shape. The charcoal gradient keeps continuity with the splash and Android background while giving the glass some light, so it does not look flat beside iOS 26's glossy icons.

The engineer chose every pick here: SVG drawn here, refined coupe, liquid plus garnish, charcoal gradient, repo source plus EAS Metadata, six locales, Latin American Spanish, pantry first positioning, name plus keyword title, native rewrite plus cross check, knowledge based keywords, promotional text, release notes, URLs from one constant, the privacy contact section as the support URL, and a closing age line.
