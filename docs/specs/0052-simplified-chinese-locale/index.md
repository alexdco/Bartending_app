# 0052. Simplified Chinese locale

**Date**: 2026-11-13
**Status**: In Progress

## Summary

This spec adds Simplified Chinese (URL code `zh`, announced to browsers and search engines as `zh-Hans`) as the app's ninth language on web, mobile, the recipe catalog, recipe notes, and drink ideas, following the Korean path from spec 0051. Search needs no SQL change: the CJK "contains" step from spec 0050 already covers Chinese characters. Three things are new for Chinese: detection never hands Simplified to a visitor who asked for Traditional Chinese, a typography pass sets mainland punctuation and spacing, and a script check keeps Traditional characters and Japanese kana out of the text. Drinks with no settled Chinese name keep their English name. There is no human review: a second AI pass on a stronger model, plus the automated checks, gates the launch.

The decision history (context, options considered, and rationale) lives in [rationale.md](rationale.md).

## Requirements

**User stories**:
- As a Chinese speaking home bartender, I want to browse, search, and read recipes and the app itself in natural, friendly Simplified Chinese.
- As a Chinese user, I want typing 金汤力 or just 汤力 to find the gin and tonic, and drink names written the way mainland bars write them.
- As a visitor whose browser or phone asks for Traditional Chinese, I do not want to be switched to Simplified without choosing it.
- As the engineer, I want Chinese to launch without a native reviewer, with an AI second pass and checks I can trust instead.

**Acceptance criteria**:
- **AC-1**: `zh` is a supported locale. Every string in the web message catalog and the mobile resource file renders in Simplified Chinese under `/zh/...` on web and when `zh` is the active language on mobile. Strings address the reader as 你 (never 您), keep buttons and labels as short words (保存, 搜索), use half width digits, full width Chinese punctuation (，。？！：；) and `“ ”` quotes, and put one space between a Chinese character and a Latin letter or digit. In UI strings, a number placeholder next to a Chinese character gets a space (`{count} 个`, `# 个`, mobile `{{count}} 个`), and a text placeholder such as `{name}` gets none (`{name}已保存`). Chinese AI output (catalog text, notes, drink ideas) passes through `normalizeChineseTypography` before it is stored or returned.
- **AC-2**: Recipe name, instructions, glass, ingredient measures, ingredient and tag names, and the three recipe notes render in Chinese when a `zh` translation exists. Otherwise they render in English, never another language, never blank, never an error. A drink with no established Chinese name has a `zh` name equal to its English name; that is a translation, not a fallback.
- **AC-3**: Chinese search works through the existing tiers with no SQL change. On `/zh`, any query holding a Han character runs the spec 0050 CJK contains step, so 金汤力 and 汤力 each find a recipe whose `zh` name is 金汤力 (or whichever real catalog name holds those characters), and `search_ingredients` finds an ingredient whose `zh` name contains the query, prefix matches first, with the staples filter applied. A Latin query on `/zh` (Margarita, Jamaica Kiss) finds the recipe through the English name. A query typed in Traditional characters (瑪格麗特) finds only names that share those exact characters; that is accepted (Traditional to Simplified folding is a follow up). Example names in tests come from the real `zh` catalog after the backfill.
- **AC-4**: Adding Chinese puts no locale code or config name into any SQL function body, and changes no SQL function. The only Chinese database change is the `('zh', 'simple')` row in `supported_locales`. The `pg_proc` structure query from [0045 verify.md](../0045-language-agnostic-locales-portuguese/verify.md), with its pattern widened to `'(es|pt|fr|ru|hi|ja|ko|zh|spanish|portuguese|french_unaccent|russian|hindi|simple)'` (quoted literals only), finds no match in any function body.
- **AC-5**: English, Spanish, Portuguese, French, Russian, Hindi, Japanese, and Korean behave exactly as before: their search results, names, instructions, measures, notes, slugs, fonts, CSS, and detection are unchanged. Every existing `parseAcceptLanguage` test passes untouched.
- **AC-6**: The locale parity test passes with `zh` in `SUPPORTED_LOCALES`, the `supported_locales` seed, and `generate-drink-idea`'s list, and with `LOCALE_TEXT_SEARCH_CONFIG.zh` equal to `"simple"`.
- **AC-7**: While `zh` is not in `LAUNCHED_LOCALES`, it follows spec 0045 AC-7 and AC-8: no 简体中文 in the web menu or the production mobile language card, never picked by detection, absent from the sitemap and every hreflang alternate, and `/zh/...` pages render with `noindex`, a self canonical, and no alternates. Mobile dev and preview builds list 简体中文.
- **AC-8**: Once launched, detection picks `zh` for a Simplified or unmarked Chinese language tag and never for a Traditional one, on web and mobile, through one shared helper `localeForLanguageTag`:
  - A tag is **Traditional** when its primary subtag is `zh` and either it has the script subtag `Hant`, or it has no `Hans` subtag and its region is `TW`, `HK`, or `MO` (`zh-TW`, `zh-HK`, `zh-MO`, `zh-Hant`, `zh-Hant-CN`). Matching ignores case. The Traditional test alone also accepts `_` between subtags (`zh_TW`); the primary subtag is still read as `tag.split("-")[0]`, exactly as today, so an underscore tag (`zh_TW`, `zh_CN`, `es_ES`) picks no locale, as before.
  - Every other `zh` tag picks `zh` (`zh`, `zh-CN`, `zh-SG`, `zh-MY`, `zh-Hans`, `zh-Hans-HK`).
  - On web, a Traditional tag is skipped and the next language in the `Accept-Language` list is tried. After a Traditional tag has been seen, a later bare `zh` (no script, no region) is skipped too, so Taiwan Chrome's default `zh-TW,zh;q=0.9,en-US;q=0.8,en;q=0.7` lands on `en`. A later explicit Simplified tag (`zh-CN`, `zh-Hans`, `zh-SG`) still picks `zh`.
  - On mobile, detection still reads only the first device language, now through `localeForLanguageTag(primary.languageTag)`; a Traditional first language gives English.
  - A stored preference of `zh` (cookie, AsyncStorage, `user_preferences.locale`) is always honored once launched; the Traditional rule applies to detection only. Anyone can still choose 简体中文 in the switcher.
  - Hreflang, the sitemap, and `<html lang>` announce `zh-Hans`, and the switcher shows "简体中文" whatever the active language.
- **AC-9**: A `/zh` recipe link uses the English name slug through the existing `base_name` fallback (spec 0048 AC-9): a recipe named 玛格丽特 links to `/zh/recipes/margarita-<uuid>`, its canonical and sitemap entry use the same slug, and a card click never takes a redirect. A recipe whose `zh` name is the kept English name gives the same slug. No change to `buildRecipeSlugPath`.
- **AC-10**: On web, `/zh` pages render body text with Inter for Latin characters and Noto Sans SC for Chinese, and headings (the brand wordmark and Latin letters in headings included) in Noto Serif SC 600. Every character in the shipped `zh` UI strings and catalog renders in a Noto SC face or Inter, not a system fallback, checked by a render check on `/zh`. The Noto SC `@font-face` rules reach `/zh` only, through `/fonts/zh/fonts.css`, which the layout links only when the locale is `zh`; every other locale downloads neither that stylesheet nor any Noto SC file, and its production CSS contains no Noto SC `@font-face` rule (enforced by the widened postbuild check). Nothing is requested from Google's servers at runtime. In every other locale, the switcher's "简体中文" option carries `lang="zh-Hans"` and renders in the system Simplified Chinese font.
- **AC-11**: On `/zh`, text wraps between characters with `line-break: strict` (no line starts with closing punctuation such as ，。” or ）), every text style uses the `--leading-*` values from `:root:lang(zh-Hans)`, and no recipe card, chip, button, or pantry row overflows its container or the page at 360 px, including cards whose name is a long kept English name.
- **AC-12**: The plural forms test from spec 0047 passes with `zh`, and `packages/shared/src/pluralForms.test.ts` gains a `["zh", ["other"]]` row. The i18next Node test returns the `_other` string for `zh` counts 0, 1, 2, and 5.
- **AC-13**: Unit labels show `ml`, `cl`, `L`, `盎司` in `zh`. Batch labels (parts label «份») and the drink idea limit copy have hand written Chinese values. Measures keep the dot decimal.
- **AC-14**: `translate-catalog --locale zh` translates the catalog with the pinned terms in `LOCALE_AI_TERMS.zh`, and hash gating works per locale, so a second run translates nothing. After the backfill, across the four translation tables' `zh` rows: every recipe whose English ingredients include lime shows 青柠 and every lemon recipe shows 柠檬; no row contains a character from `TRADITIONAL_ONLY_CHARACTERS`, a kana (U+3041 to U+30FF, leaving out `・` U+30FB and `ー` U+30FC), or a Hangul character; no name field (recipe name, glass, ingredient, tag) has a middle dot (`·` U+00B7, `・` U+30FB, `･` U+FF65, `•` U+2022, `‧` U+2027, `∙` U+2219) next to a Han character. A recipe or ingredient name is either Chinese (it holds a Han character) or exactly the English source name: when the model returns a name with no Han character, the pipeline stores the English source name as is, so case, apostrophes, and `&` never drift. Brand and proprietary ingredient names (Galliano, Angostura, 7-Up) stay in English. Tag and glass names are always Chinese. A row that fails a check is fixed by rerunning `translate-catalog --locale zh --ids <uuid>,…` on those ids (`--ids` already ignores the hash gate), never by hand editing. No `zh` row or UI string contains a term from `CHINESE_BANNED_TERMS` (您, 莱姆, 琴酒, 兰姆酒, 青柠檬). After launch, the import job translates new recipes into `zh` too.
- **AC-15**: `propose-recipe-notes --locale zh` proposes Chinese notes for empty `zh` fields only, into `recipe-notes-proposals.zh.json`. The AI second pass (AC-20) reads every note before `apply-recipe-notes --locale zh` runs, and the apply writes only `zh` rows.
- **AC-16**: The web admin recipe form shows a Chinese notes section, and saving it updates only that recipe's `zh` row.
- **AC-17**: `generate-drink-idea` accepts `locale: "zh"` and writes the drink idea natively in Simplified Chinese with the pinned terms, passing it through its own copies of `normalizeChineseTypography` and `normalizeChineseName`. Pantry verification still checks the English `source_name` only.
- **AC-18**: `user_preferences.locale` accepts `'zh'`, syncs, and follows the sign in merge rule from spec 0020 AC-16. Before launch, a stored `zh` preference counts as absent for detection and is left in place.
- **AC-19**: The `/zh` Open Graph share image is the English share image (English tagline, Fraunces), with English alt text and metadata. Every other locale's image is unchanged.
- **AC-20**: Before launch, an AI second pass runs in a Claude Code session on a stronger model than the one that drafted the text (Opus, not Haiku), against the written checklist in this spec's `verify.md`. It reads `LOCALE_AI_TERMS.zh` and the edge function sentence before the backfill, then the full web and mobile `zh.json`, the placeholder message list from spec 0047 AC-12, the unit, batch, and limit copy, every `zh` recipe name and every `zh` ingredient name beside its English source (to catch an invented name, or a plain word left in English), a 30 recipe sample of the rest of the catalog backfill, 10 live drink ideas, and every note in `recipe-notes-proposals.zh.json`. Each finding is fixed or recorded as accepted, and `verify.md` records the model, the date, and the outcome. No human review is required.
- **AC-21**: On a real iOS device and a real Android device, both with English as the system language, with the app set to `zh`, Chinese renders with no clipped lines on the recipe screen, the pantry, and the account screen; the characters 直, 骨, and 角 show their mainland Chinese forms (not the Japanese ones); a line that mixes them with Simplified only characters (门, 饮, 调) reads as one typeface, not two; and a rating count of 1 and of 2 both show the `_other` string.
- **AC-22**: All Chinese text written by AI or pinned in `LOCALE_AI_TERMS.zh` and the edge function instruction is stored in Unicode NFC, with no full width digits or Latin letters, no ideographic space, and no Japanese quotes (`「」` `『』`). A vitest scan over both `zh.json` files enforces the same rules plus no `TRADITIONAL_ONLY_CHARACTERS` character, no kana, and no Hangul, so the UI strings are checked automatically, not only by the AI pass.
- **AC-23**: Launch is one commit that adds `"zh"` to both `LAUNCHED_LOCALES` and `CATALOG_TRANSLATION_LOCALES`, made only after the catalog backfill, the notes apply, and the AI second pass are recorded in `verify.md`. A mobile build ships with it, and the production sitemap and hreflang show `zh-Hans`.
- **AC-24**: Feature 60 lists Simplified Chinese among its store listing locales. The web launch does not wait on it.

## Decision

**Chosen option**: Option 1: The Korean path, with Traditional aware detection, a Chinese typography pass, and a curated script check.

Chinese is added as code `zh` (hreflang `zh-Hans`) with the `simple` config and no SQL function change, gated behind `LAUNCHED_LOCALES`. Search reuses the spec 0050 CJK contains step as it is, with no Traditional to Simplified folding. One shared helper keeps Traditional Chinese visitors off the Simplified pages unless they choose them. Web loads Noto Sans SC and Noto Serif SC 600 from a third entry in `script-fonts.config.mjs`, linked only on `/zh`. `normalizeChineseTypography` sets mainland punctuation, quotes, and spacing; `normalizeChineseName` removes middle dots from names; a curated list of Traditional only characters backs a string scan and a SQL catalog check. An Opus pass against a written checklist stands in for the native review.

**Implementation skills**: `supabase-postgres-best-practices` (`supabase/agent-skills`, `.agents/skills/supabase-postgres-best-practices/`) · `nextjs-app-router-patterns` (`wshobson/agents`, `.agents/skills/nextjs-app-router-patterns/`) · `react-native-best-practices` (`callstackincubator/agent-skills`, `.agents/skills/react-native-best-practices/`) · `vitest` (`antfu/skills`, `.agents/skills/vitest/`)

## Feature design

| `recipe_translations`, `ingredient_translations`, `tag_translations`, `recipe_ingredient_translations` (new rows only) | unchanged | `locale = 'zh'` rows from the backfills; `name_search` set by the existing trigger with `simple` | `locale` → `supported_locales(code)`, unchanged | N:1, unchanged |

**Shared TS surface (`packages/shared/src/`)**:
- `locale.ts` maps: `SUPPORTED_LOCALES` gains `"zh"`; `LOCALE_TEXT_SEARCH_CONFIG.zh = "simple"` (comment: no Chinese stemmer; names have no spaces, so the CJK contains tier does the matching, spec 0052 AC-3); `LOCALE_HREFLANG.zh = "zh-Hans"`; `LOCALE_AI_LANGUAGE.zh = "Simplified Chinese as written in mainland China"`; `LOCALE_NATIVE_NAME.zh = "简体中文"`. `LAUNCHED_LOCALES` and `CATALOG_TRANSLATION_LOCALES` unchanged until launch. The header comment lists this spec.
- `locale.ts` detection (AC-8), all pure:
  - `isTraditionalChineseTag(tag: string): boolean`: lower case the tag, split on `-` or `_`; true when part 0 is `zh` and (the parts include `hant`, or the parts do not include `hans` and include `tw`, `hk`, or `mo`).
  - `localeForLanguageTag(tag: string | null | undefined, allowed: readonly Locale[] = LAUNCHED_LOCALES): Locale | null`: `null` for an empty tag or a Traditional tag; otherwise the lower cased tag's primary subtag, read as `tag.split("-")[0]` (hyphen only, as `parseAcceptLanguage` does today), when it is a supported locale in `allowed`, else `null`. So `es_ES` and `zh_CN` give `null`, as they do today. Exported from the barrel.
  - `parseAcceptLanguage` keeps its signature and loops the candidates as today, but returns `localeForLanguageTag(tag, allowed)` when not `null`, and tracks one flag: once a candidate is a Traditional tag, any later candidate that is exactly `zh` is skipped. No other locale's result can change, since the helper equals today's primary subtag rule for every tag that is not Traditional Chinese.
  - This is the one place a locale code appears in detection logic. It is TypeScript, not SQL, so the 0045 no locale in SQL rule holds. Keep the Chinese rule inside `isTraditionalChineseTag` only.
- `LOCALE_AI_TERMS.zh`, drafted as below, then checked by the AI second pass before the backfill (the edge function carries a hand copy of the register, citrus, name, and punctuation sentences):
  - Write natural Simplified Chinese as used in mainland China; never use Traditional characters or Taiwan and Hong Kong wording (never «莱姆» for lime, «琴酒» for gin, or «兰姆酒» for rum).
  - Address the reader as «你», never «您»; write recipe steps as short commands with no pronoun (加入冰块，摇匀).
  - Lime is «青柠» and lemon is «柠檬»; keep them distinct. Lime juice is «青柠汁». Lemon lime soda is «柠檬青柠汽水», never «柠檬水».
  - Spirits and staples: gin «金酒», vodka «伏特加», rum «朗姆酒», tequila «龙舌兰», whiskey «威士忌», brandy «白兰地», vermouth «味美思», liqueur «利口酒», bitters «苦精», simple syrup «糖浆», club soda «苏打水», ice «冰块».
  - Bar tools: shaker «摇酒壶», jigger «量酒器», muddler «捣棒», strainer «滤冰器», bar spoon «吧勺».
  - Glasses: old fashioned glass «古典杯», cocktail glass «鸡尾酒杯», collins glass «柯林斯杯», highball glass «高球杯».
  - Measures: a dash is «抖», a drop is «滴», a shot is «一口杯» (the AI terms pass confirms this word before the backfill), a part is «份», a teaspoon is «茶匙», a tablespoon is «汤匙»; use the same word in the measures and the steps.
  - Brand and proprietary names (Galliano, Angostura, 7-Up, Southern Comfort) stay in English exactly as given. These term and name rules apply to ingredient and tag names too, not only to full sentences.
  - Cocktail names: use the established mainland Chinese name where one exists (玛格丽特, 莫吉托, 金汤力, 曼哈顿, 尼格罗尼, 大都会); when no established Chinese name exists, keep the English name exactly as given, and never invent a translation or a sound based spelling. Never put a middle dot in a name (汤姆柯林斯, not 汤姆·柯林斯). Lime is never «青柠檬».
  - Typography: half width digits; units `ml`, `cl`, `L`, and «盎司», with a space between the number and the unit (30 ml); full width punctuation (，。？！：；) with no space around it; «“ ”» for quotes; one space between a Chinese character and a Latin letter or digit.
- `chineseScript.ts` (new, with `chineseScript.test.ts`):
  - `TRADITIONAL_ONLY_CHARACTERS: string`, a curated constant of at least 300 distinct, high frequency Traditional characters whose Simplified form is a different character and which are not themselves used in standard Simplified Chinese (so 著, 乾, 藉, 瞭, 麽 and other characters valid in both are left out). It must include this bar and app set: 麗瑪龍蘭檸萊薑鹽醬蘋櫻藍綠紅黃熱涼凍搖攪濾壓擠滿飲雞調類級蘇釀葉塊顆個們這為與來時會後裡麼開關譜單選儲櫃購買賣評論語設錄帳戶驗證隱載歡應無鐘點頁請讓說給過還進適. The build drafts the rest from the most frequent Traditional characters; the AI second pass reads the list once for a character that is valid Simplified.
  - `hasTraditionalCharacter(text: string): boolean` and `findTraditionalCharacters(text: string): readonly string[]` (distinct hits, for test messages).
  - `TRADITIONAL_ONLY_SQL_CLASS: string`, the same characters as a Postgres bracket class (`[麗瑪…]`), so the catalog check in `verify.md` is pasted from one source. A unit test prints nothing but asserts the class holds exactly the constant's characters.
  - `CHINESE_BANNED_TERMS: readonly string[]` = `["您", "莱姆", "琴酒", "兰姆酒", "青柠檬"]` (the wrong register and the regional or wrong words that are written in Simplified characters, so the character list cannot see them), with `findBannedChineseTerms(text): readonly string[]`. The strings scans and a catalog SQL check (one `like` per term, written into `verify.md`) use it. The pinned sentences in `LOCALE_AI_TERMS.zh` and `CHINESE_INSTRUCTION` name these words on purpose and are not scanned.
  - `keepSourceNameUnlessChinese(translated: string, source: string): string`: returns `translated` when it holds a Han character, else `source` unchanged.
  - Tests: every listed character is distinct; none appears in a Simplified fixture paragraph (a few hundred characters of ordinary Simplified text, including the pinned terms); the must include set is present; `findBannedChineseTerms` finds 青柠檬 and passes 青柠 and 柠檬; `keepSourceNameUnlessChinese("jamaica kiss", "Jamaica Kiss")` is `"Jamaica Kiss"` and `("玛格丽特", "Margarita")` is `"玛格丽特"`.
- `chineseTypography.ts` (new, with `chineseTypography.test.ts`, a header comment like `koreanTypography.ts`). Han means U+3400 to U+4DBF, U+4E00 to U+9FFF, and U+F900 to U+FAFF. Two pure, idempotent exports; this is the one rule list (the edge function copies match it exactly):
  - `normalizeChineseTypography(text: string): string`, for every Chinese AI text field, applying in order:
    1. `normalize("NFC")`.
    2. Full width digits and Latin letters (U+FF10 to U+FF19, U+FF21 to U+FF3A, U+FF41 to U+FF5A) to half width (`１５` → `15`, `ＧＩＮ` → `GIN`); the ideographic space U+3000 to a normal space. Full width punctuation is left alone.
    3. `「` and `『` to `“`; `」` and `』` to `”`.
    4. A straight `"…"` pair (no newline inside) whose inner text holds Han becomes `“…”` with the inner text trimmed.
    5. A sentence ending `.` becomes `。`, by the same rule as `normalizeJapaneseTypography`: after a Han character or `”`, or after an ASCII letter, digit, `%`, or `)` when its line holds Han, and followed by the end of the text, a newline, or (after optional spaces) a Han character. A dot between two digits never matches.
    6. `,` `?` `!` `:` `;` become `，` `？` `！` `：` `；` in two cases: directly after a Han character or `”`; or after an ASCII letter, digit, `%`, `)` or `）` (optional spaces between) when the line holds Han and what follows, after optional spaces, is a Han character, the end of the text, or a newline (`加入 30 ml, 摇匀` → `加入 30 ml，摇匀`). `1:1`, `10:30`, and URLs never match, since a digit or letter follows.
    7. Spaces and tabs directly before or after a full width `，。？！：；、` are removed; spaces between two Han characters are removed. Newlines are never touched.
    8. One space is inserted between a Han character and an ASCII letter or digit, in either order, when they touch (`加入30 ml金酒` → `加入 30 ml 金酒`, `用Boston摇酒壶` → `用 Boston 摇酒壶`). Nothing is inserted next to punctuation, brackets, or `%`, or between a digit and a Latin unit (`30ml` stays). A digit touching a Chinese unit or measure word does get the space (`30盎司` → `30 盎司`, `2滴` → `2 滴`), which matches the pinned style.
    Decimals, `30ml` and `30 ml`, `1:1` between digits, URLs, `B-52`, parentheses of either width, any middle dot, and Latin only text are left alone.
  - `normalizeChineseName(text: string): string`, for name fields only: `normalizeChineseTypography`, then any run of optional spaces, one dot from the set `·` U+00B7, `・` U+30FB, `･` U+FF65, `•` U+2022, `‧` U+2027, `∙` U+2219, and optional spaces is removed when a Han character is on either side, then step 8 runs again and leading and trailing spaces are trimmed (`汤姆·柯林斯` → `汤姆柯林斯`, `金·Tonic` → `金 Tonic`, `B·52` unchanged).
- `catalogTranslation.ts`: `localeTypography` gains `if (locale === "zh") return normalizeChineseTypography;` and `localeNameTypography` gains `if (locale === "zh") return normalizeChineseName;`, with their doc comments naming Chinese (spec 0052 AC-1, AC-14). The existing name call sites (recipe `name` and `glass`, ingredient `name`, tag `name`) already use `localeNameTypography`. One call site change: for `zh` only, the recipe `name` and the ingredient `name` pass through `keepSourceNameUnlessChinese(typesetName(translated), sourceName)` before the upsert (AC-14); glass and tag names do not. Nothing in the pipeline rejects a translated name equal to its source, and `LOCALE_AI_TERMS[locale]` already reaches the name prompt (`nameTranslationPrompt`), after its line saying style notes are for full sentences; the last pinned sentence above is what tells the model the terms apply to names too.
- **Failed check remedy**: the normalizers do not convert Traditional characters or remove kana. A catalog row that fails an AC-14 SQL check is fixed by rerunning `translate-catalog --locale zh` on those ids; a failing note is fixed in the proposals file by the AI pass before the apply; a drink idea with a Traditional character is a finding the AI pass records and fixes in the edge function instruction.

**Key invariants**:
- All 0045 to 0051 invariants hold. No SQL function body names `zh`; no SQL function changes.
- `localeForLanguageTag` returns the same result as the old primary subtag rule for every tag that is not Traditional Chinese.
- Detection never picks `zh` from a Traditional tag, or from a bare `zh` that follows one; a stored `zh` preference always wins once launched.
- No `zh` catalog row or UI string contains a `TRADITIONAL_ONLY_CHARACTERS` character, a kana, or a Hangul character, and no `zh` name field has a middle dot next to a Han character.
- A `zh` recipe or ingredient name holds a Han character or equals its English source name exactly (`keepSourceNameUnlessChinese`); an invented Chinese spelling is caught only by the AI pass, which reads every name.
- No `zh` catalog row or UI string holds a `CHINESE_BANNED_TERMS` term.
- `localeNameTypography` equals `localeTypography` for every locale except `ko` and `zh`.
- Every other locale's CSS, fonts, and search results are unchanged; no locale except `zh` links `/fonts/zh/fonts.css`.
- `zh` joins `LAUNCHED_LOCALES` and `CATALOG_TRANSLATION_LOCALES` in one commit, only after the AI second pass is recorded.
- The edge function's Chinese instruction duplicates `LOCALE_AI_TERMS.zh` by hand; a change to one changes the other in the same commit.
- Both Chinese normalizers are idempotent, their edge function copies match them, and their output is NFC.

**Security model**: no change. `supported_locales` stays read only for `anon` and `authenticated`; no function, grant, or policy changes. No new PII. Compliance: Simplified Chinese is a language, not a market. This spec does not target mainland China: it adds no hosting there, no ICP filing (the licence a site needs to be hosted in mainland China), and no change to the age gate, and PIPL (China's privacy law) is out of scope. The site may be slow or unreachable from the mainland, which is accepted. Targeting China later needs its own legal and hosting review first.

**Configuration required**: no env vars or secrets. The web build fetches the SC fonts from `fonts.googleapis.com` and `fonts.gstatic.com` in `prebuild`, as it already does for JP and KR.

## Migration plan

**Strategy**: feature flagged (`LAUNCHED_LOCALES`), one additive migration.
**Phases**: the `zh` row insert (step 1); backfills that only insert `zh` rows (steps 2 and 3).
**Rollback**: Chinese is invisible until step 5, so fix forward. For a full revert, the Chinese down SQL deletes the `zh` rows from the four translation tables, sets `user_preferences.locale` to null where it is `'zh'`, and deletes the `zh` row from `supported_locales`. The detection helper change is behavior neutral for the other eight locales and can stay.
**Risks**: low. No search function changes. The detection helper touches a path every visitor takes, so its tests must show the old results for every existing header. The main content risk is text quality launched without a human reader, which the AI pass, the script list, and the SQL checks reduce but do not remove.

## Consequences

**Positive**:
- Chinese ships with no SQL function change; the spec 0050 CJK step pays off a third time.
- Traditional Chinese visitors are not handed Simplified by surprise, and the helper is the natural home for a later Traditional locale.
- Drink names read the way mainland menus do, with no invented spellings.
- Launch does not wait on finding a reviewer.

**Negative / tradeoffs**:
- No human has read the Chinese text. Legal strings (age gate, privacy) and notes are checked only by a second model.
- A query typed in Traditional characters finds little, until the folding follow up ships.
- Many drink names on `/zh` stay in English, so those pages look partly untranslated.
- The Traditional list is curated, not complete: a rare Traditional character outside it can ship.
- Detection now holds one rule that names a language, the first of its kind in `locale.ts`.
- Two more web fonts on `/zh`, likely the largest script font set so far, and one extra render blocking stylesheet there.
- The `/zh` share image is in English. `/zh` URLs carry English words.
- Recipe text is machine translated. Learn and quizzes stay English under `/zh/`.
- Nine languages means more translation cost and one more string owed for every future feature.

**Neutral**:
- The default notes run's file gains a `zh` block at launch.
- The postbuild matcher now names three scripts.
- `<html lang>` and hreflang for Chinese carry a script subtag (`zh-Hans`), the first locale after `pt-BR` whose announced code differs from its URL code.
