# 0007. AI generated pantry drink ideas

**Date**: 2026-09-07
**Status**: In Progress

## Summary

This spec lets a user turn their pantry contents into a brand new, never before seen drink idea, generated by an AI model (Claude), instead of only browsing the existing recipe catalog. The idea is always shown as an extra option next to the real recipe matches from spec 0006, uses only ingredients the user already has, and is never saved anywhere, it is shown once per request. A daily limit per person keeps the cost of calling the AI model bounded and predictable.

## Requirements

**User stories**:
- As a guest or signed in user with ingredients in my pantry, I want to ask for a brand new drink idea made only from what I have, so I get inspiration beyond the existing recipe catalog.
- As a user, I want it to be obvious that a generated idea is AI made, not a real recipe from the catalog, so I am not misled about its source.

**Acceptance criteria**:
- **AC-1**: A user with at least one pantry ingredient can trigger a generation from the drink ideas page (spec 0006) and receives a plausible original recipe with a name, an ingredient list with rough amounts, and numbered steps, built only from ingredients already in their pantry.
- **AC-2**: The generated recipe is visibly labeled as AI generated, distinct from a real catalog recipe (spec 0004).
- **AC-3**: A user with an empty pantry (or one with too few ingredients, see Key invariants) does not see a way to trigger a generation; they see the same empty state as spec 0006, linking to the pantry page.
- **AC-4**: Each user is limited to 10 generations per UTC calendar day, enforced server side and keyed to their user id; a user who reaches the limit gets a clear, retryable message naming when it resets, never a silent failure or a client bypassable check.
- **AC-5**: A generated result is not persisted anywhere; leaving the page or refreshing loses it, and asking again produces a new, independent result.
- **AC-6**: A user with no active session (the same condition as spec 0006's AC-6) sees the same retryable error state as a failed pantry action, never a silent empty or default result.
- **AC-7**: If the AI call fails, times out, or returns a result that does not match the expected recipe shape, the user sees a clear, retryable error instead of a broken or partial recipe; a single automatic retry happens first, transparent to the user.
- **AC-8**: A user's generated idea is built only from their own pantry; no client can see, influence, or trigger a generation against another user's pantry or quota.

## Decision

**Chosen option**: Option 1: Structured output via Anthropic's `messages.parse()` with a Zod schema

**Implementation skills**: `sentry-get-started` (`getsentry/sentry-for-ai`, `.agents/skills/sentry-get-started/`) · `supabase-postgres-best-practices` (`supabase/agent-skills`, `.agents/skills/supabase-postgres-best-practices/`)

## Feature design

**Data model sketch**:

One new table; no changes to existing tables.

| Entity | Primary key | Fields | Foreign keys | Cardinality |
|---|---|---|---|---|
| `ai_generation_quota` | (`user_id`, `day`) | `day` (`date`, not null, default `(now() at time zone 'utc')::date`, always computed in SQL, never passed in by application code); `count` (int, not null, default 0) | `user_id` → `auth.users` | one row per user per UTC calendar day |

**State transitions**: none; `count` only ever increases, reserved atomically before each generation attempt (see Key invariants), never decremented or reset by anything other than the day changing (a new day is a new row).

**API surface**:
| Endpoint | Method | Key inputs | Key outputs | Auth | Key errors |
|---|---|---|---|---|---|
| `generate-drink-idea` (new Supabase Edge Function) | POST | none required (the function reads the caller's own pantry via their JWT; body may be empty) | `{ name: string (max 60 chars), ingredients: [{ name: string, amount: string }] (1 to 8 items), steps: string[] (1 to 10 items) }` | anonymous or signed in session required, sent as the caller's JWT in the `Authorization` header (the same header `supabase.functions.invoke()` sends automatically for a signed in Supabase client) | 401 no/invalid session; 422 pantry too small to generate from; 429 quota exceeded (body names `resetsAt`); 502 generation failed after one retry |

**Value sourcing**:
| Action | Value produced / displayed | Source |
|---|---|---|
| Generate button, drink ideas page | Whether the button is shown at all | Client side: the same `usePantry()` result (spec 0005) already loaded on that page; shown only when the pantry has at least the minimum ingredient count (Key invariants) |
| Generated recipe card | Name, ingredients with amounts, numbered steps | `messages.parse()`'s validated output, built by Claude Haiku (`claude-haiku-4-5`, `max_tokens: 1024`, no thinking) from the caller's own pantry ingredient names, fetched server side inside the function via `auth.uid()` (never sent by the client); every ingredient name Claude returns is checked (case and whitespace normalized) against that same pantry list before the result is returned, a mismatch is treated as a schema failure and consumes the one retry (AC-1, AC-7) |
| Generated recipe card | The "AI generated" label | Static client side copy/badge on the result component; always true for anything this endpoint returns, no server flag needed |
| Quota exceeded message | The exact time the limit resets | Computed server side as the start of the next UTC calendar day, returned as `resetsAt` in the 429 body |
| No session error | The retryable error state | Same client pattern as spec 0006's AC-6: the function returns 401, the client shows the same retry affordance as a failed pantry/match request |

**Key invariants**:
- The function never accepts a pantry ingredient list from the caller; it always resolves the caller's own pantry server side via `auth.uid()`, so a generation can never be computed against, or reveal, another user's pantry (AC-8).
- A pantry with fewer than 2 ingredients is "too small to generate from"; the client hides the Generate action in that case (AC-3), and the function itself also rejects such a request with 422 as a server side backstop, so a client that skips its own UI check still cannot trigger a generation from too small a pantry.
- The prompt constrains Claude to use only the ingredients present in the caller's pantry, and the function verifies this after the fact (see Value sourcing): a response naming an ingredient outside the pantry is never shown to the user as is.
- The quota is reserved atomically, before the Claude call, not incremented after success: one statement (`insert into ai_generation_quota (user_id, day, count) values (auth.uid(), current UTC date, 1) on conflict (user_id, day) do update set count = ai_generation_quota.count + 1 where ai_generation_quota.count < 10 returning count`) both checks and claims a slot in a single round trip, so two concurrent requests from the same user cannot both pass the check (closing the race the naive "check, then increment after success" sequence would leave open). A row returned means the slot is claimed; no row returned means the limit is already reached (429). If the subsequent Claude call then fails after a slot was claimed (AC-7's retry, or the final failure), that reserved generation is not refunded; a failed attempt still costs one of the day's 10, which is the simplest rule that keeps the counter race free without a second write per request.
- The daily limit is a flat 10 generations per user per UTC calendar day, the same for anonymous and signed in users (there is no signed in tier live yet, spec 9 is still planned).
- A row in `ai_generation_quota` is never deleted automatically; the table stays small in practice (one row per active user per day) and a retention job is deferred (see Follow-up).
- The Anthropic call uses a per attempt timeout of 15 seconds; the one automatic retry (AC-7) fires only on a timeout, a schema/pantry mismatch, or a 5xx from Anthropic, never on a 4xx response (a 4xx is a request problem a retry cannot fix, e.g. an auth or billing issue on the Anthropic account), and runs immediately with no backoff delay given the short timeout budget.

**Security model**:
The function requires a valid JWT (anonymous or signed in) on every call, verified the same way Postgres RLS already verifies one for `pantry_items` and `match_recipes_to_pantry` (spec 0006): a missing or invalid JWT is a 401, not a default or empty result (AC-6). Unlike `pantry_items`, `ai_generation_quota` grants the client no policy at all, no `select`, `insert`, `update`, or `delete`: a quota counter a client could read or write is a counter a client could reset or inflate, defeating AC-4 entirely. The Edge Function is the only writer, using the Supabase service role key (a privileged key that bypasses RLS, held only server side, never sent to a client) to run the atomic reservation statement above; it still resolves the caller's own pantry through their JWT, so the service role key only ever touches the quota table, never widens what pantry data the function can see. The Anthropic API key is stored as a Supabase Edge Function secret, never sent to or reachable from either client app (carried over from spec 0001's decision).

**Configuration required**:
- `ANTHROPIC_API_KEY`: the Anthropic API key, set as a Supabase Edge Function secret, read only inside `generate-drink-idea`.
- `SUPABASE_SERVICE_ROLE_KEY`: already available to every Supabase Edge Function by default; used here specifically to write `ai_generation_quota`, since that table grants no client policy at all.
- `SENTRY_DSN` (Edge Function): the Sentry project's ingestion address, set as a Supabase Edge Function secret, so errors from this function reach the same Sentry project as the rest of the app (per root `AGENTS.md`'s existing Sentry decision).

**Critical test scenarios**:
- Happy path: a user with gin, tonic water, and lime in their pantry taps Generate and receives a named recipe using only those three ingredients, with amounts and numbered steps, labeled AI generated, verifies **AC-1**, **AC-2**.
- Empty pantry: a user with zero (or one) pantry ingredients never sees the Generate action, and the drink ideas page shows spec 0006's own empty state instead, verifies **AC-3**.
- Quota exceeded: a user who has already generated 10 ideas today gets a 429 with a clear message naming when the limit resets, and the request never reaches Claude; two concurrent requests from a user with exactly one slot left result in exactly one success and one 429, never two successes, verifies **AC-4**.
- Failure case: the Anthropic call times out (simulated), the function retries once automatically, and if it still fails the user sees a clear retryable error, never a partial or malformed recipe, verifies **AC-7**.
- Auth/permission: a request with no valid JWT gets a 401 and the same retryable error state as a failed pantry action; a second user's generation never increments or is affected by the first user's quota row, verifies **AC-6**, **AC-8**.

## Build plan

1. Migration: add `ai_generation_quota (user_id, day, count)`, composite primary key `(user_id, day)`, RLS enabled with no policies granted to `anon`/`authenticated` (the Edge Function's service role key is the only writer or reader), satisfies **AC-4**, **AC-8**.
2. `generate-drink-idea` Supabase Edge Function: verify the caller's JWT (401 if missing/invalid), read the caller's own pantry via `auth.uid()`, reject with 422 if fewer than 2 ingredients, atomically reserve a quota slot via the `insert ... on conflict ... where count < 10 returning` statement before calling Claude (429 with `resetsAt` if no row returned), call Claude Haiku via `messages.parse()` with a Zod schema for the recipe shape, verify returned ingredients against the pantry, retry once (only on timeout/schema-mismatch/5xx, never on a 4xx) then 502, report errors to Sentry, satisfies **AC-1**, **AC-4**, **AC-6**, **AC-7**, **AC-8**.
3. Shared `generateDrinkIdea.ts` in `packages/shared`: a thin fetch wrapper calling `supabase.functions.invoke("generate-drink-idea")`, mapping the response (including the 429/502/401 error shapes) to a typed result both apps consume the same way, satisfies **AC-1**, **AC-6**, **AC-7**.
4. Generate action and result card on the drink ideas page (spec 0006), both apps: the button is shown only when the pantry meets the minimum ingredient count (else the existing empty state), a loading state while generating, the result rendered with a clear AI generated label, and the retryable error states for AC-4/AC-6/AC-7, satisfies **AC-1**, **AC-2**, **AC-3**, **AC-4**, **AC-6**, **AC-7**.
5. Cross platform parity check: same shared fetch wrapper and the same live `generate-drink-idea` call on both apps, mirroring specs 0004 through 0006's own parity step.

## Consequences

**Positive**:
- Gives every user, even one whose pantry produces no strong catalog match, something useful to do on the drink ideas page instead of a dead end.
- The quota table and RLS shape exactly mirror `pantry_items`, so there is no new security pattern to review, only a new table following an already trusted one.

**Negative / tradeoffs**:
- This is the project's first Supabase Edge Function, first external AI call, and first Deno build target; the team is paying a one time setup cost (local Edge Function dev workflow, secrets, deploy) that every later AI feature (recipe recommendations, spec 10) can then reuse.
- A flat 10/day limit for every user, anonymous included, means a single browser's local storage clearing and re-bootstrapping a new anonymous session is a way to get more generations; this is an accepted, low value abuse vector for a free creative feature, not a security bypass of anything sensitive, and is cheap to tighten later (e.g. device fingerprinting) if it becomes a real cost problem.
- Ephemeral results (AC-5) mean a user who loved a generated idea has no way to get it back; revisiting that trade off is future scope, not this slice's job.

**Neutral**:
- `ai_generation_quota` is a small, standalone table; it does not change or relate to any existing table.
- Sets the pattern (Edge Function plus quota table plus Sentry) that spec 10 (recipe recommendations) or any future AI feature can follow directly.
