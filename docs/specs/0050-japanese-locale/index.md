# 0050. Japanese locale

**Date**: 2026-11-11
**Status**: In Progress

## Summary

This spec adds Japanese (code `ja`) as the app's seventh language on web, mobile, the recipe catalog, recipe notes, and drink ideas, following the Hindi path from spec 0048. Japanese is written without spaces between words and Postgres has no Japanese search setting, so search gains one new matching step that looks for the typed text anywhere inside a Japanese name. That step runs only when the query holds Japanese, Chinese, or Korean characters, so every other language searches exactly as before, and Korean and Chinese (features 73 and 74) reuse it with no further SQL. Web loads Noto Sans JP and Noto Serif JP on `/ja` only, recipe URLs use the English name (the `base_name` fallback from spec 0048), the share image stays English, and Japanese stays hidden until a native speaker signs off.

The decision history (context, options considered, and rationale) lives in [rationale.md](rationale.md).

## Requirements

**User stories**:
- As a Japanese speaking home bartender, I want to browse, search, and read recipes and the app itself in natural, polite Japanese.
- As a Japanese user, I want typing ジン, じん, or ｼﾞﾝ to find ジン・トニック, and typing ジントニック (no dot) to find it too.
- As a Japanese user, I want a short query like 卵 to find drinks and ingredients that contain it.
- As a Japanese user, I want kanji to look Japanese, and headings not to break in the middle of a word.
- As the engineer, I want the CJK search step built once so Korean and Chinese add only a `supported_locales` row.

**Acceptance criteria**:
- **AC-1**: `ja` is a supported locale. Every string in the web message catalog and the mobile resource file renders in Japanese under `/ja/...` on web and when `ja` is the active language on mobile. Strings use the です・ます polite form, keep buttons and labels as short nouns or verb stems (保存, 検索), use half width digits, and punctuate with 。、 and 「」. Japanese AI output (catalog text, notes, drink ideas) passes through `normalizeJapaneseTypography` before it is stored or returned.
- **AC-2**: Recipe name, instructions, glass, ingredient measures, ingredient and tag names, and the three recipe notes render in Japanese when a `ja` translation exists. Otherwise they render in English, never another language, never blank, never an error.
- **AC-3**: When the query contains a Han, Hiragana, Katakana, or Hangul character (the `has_cjk` ranges) and its folded form is not empty, `search_recipes` also returns every recipe whose translated name in the request locale contains the query after folding both sides with `search_fold` (NFKC, hiragana to katakana, lower case, middle dots and whitespace removed). So ジン, じん, and ｼﾞﾝ all find a recipe named ジン・トニック (or whichever real catalog name contains ジン), ジントニック finds ジン・トニック, and a one kanji query finds a recipe whose `ja` name contains that kanji. Whole word matches from the `simple` config (bucket 0) still list first; within the new CJK tier, names that start with the query come before names that only contain it, and ties sort by `fame_score`. A query of only ・ or spaces returns no CJK matches. No recipe appears twice. A Latin query on `/ja` (Margarita) still finds the recipe through the English name. A CJK query on a locale with no CJK translations (such as `/en`) finds nothing new.
- **AC-4**: Under the same CJK rule, `search_ingredients` returns every ingredient whose translated name contains the folded query (for example ジン finds a ドライ・ジン ingredient, and a one kanji query finds every ingredient whose `ja` name contains it), prefix matches first (a trigram similarity above 0.5 on a non prefix name may rarely outrank a prefix, which is accepted), and the staples filter still applies. The recipe search's ingredient tier finds recipes through a Japanese ingredient name the same way; a one character query such as 氷 may match many recipes there, which is accepted, as it is for short Latin queries today. Example names in tests come from the real `ja` catalog after the backfill, not from this spec.
- **AC-5**: Adding Japanese puts no locale code or config name into any SQL function body. The Japanese database changes are the `('ja', 'simple')` row in `supported_locales`, plus the locale agnostic helpers `search_fold` and `has_cjk` and the CJK tier in `search_recipes` and `search_ingredients`, which test characters, never locales. The `pg_proc` structure query from [0045 verify.md](../0045-language-agnostic-locales-portuguese/verify.md), with its pattern widened to `'(es|pt|fr|ru|hi|ja|spanish|portuguese|french_unaccent|russian|hindi|simple)'` (quoted literals only), finds no match in any function body.
- **AC-6**: English, Spanish, Portuguese, French, Russian, and Hindi behave exactly as before. For any query with no Han, Hiragana, Katakana, or Hangul character, `search_recipes` and `search_ingredients` return identical rows in identical order before and after the CJK search migration, in every locale. Names, instructions, measures, notes, and slugs are unchanged.
- **AC-7**: The locale parity test passes with `ja` in `SUPPORTED_LOCALES`, the `supported_locales` seed, and `generate-drink-idea`'s list, and with `LOCALE_TEXT_SEARCH_CONFIG.ja` equal to `"simple"`.
- **AC-8**: While `ja` is not in `LAUNCHED_LOCALES`, it follows spec 0045 AC-7 and AC-8: no 日本語 in the web menu or the production mobile language card, never picked by detection, absent from the sitemap and every hreflang alternate, and `/ja/...` pages render with `noindex`, a self canonical, and no alternates. Mobile dev and preview builds list 日本語.
- **AC-9**: Once launched, any browser or device language whose primary subtag is `ja` (`ja`, `ja-JP`) picks `ja`. Hreflang, the sitemap, and `<html lang>` announce `ja`, and the switcher shows "日本語" whatever the active language.
- **AC-10**: A `/ja` recipe link uses the English name slug through the existing `base_name` fallback (spec 0048 AC-9): a recipe named マルガリータ links to `/ja/recipes/margarita-<uuid>`, its canonical and sitemap entry use the same slug, and a card click never takes a redirect. No change to `buildRecipeSlugPath`.
- **AC-11**: On web, `/ja` pages render body text with Inter for Latin characters and Noto Sans JP for Japanese, and headings (the brand wordmark included, Latin letters in headings too) in Noto Serif JP. Every character in the shipped `ja` UI strings and catalog renders in a Noto JP face, not a system fallback, checked by a render check on `/ja`. The Noto JP `@font-face` rules reach `/ja` only, through one self hosted stylesheet the layout links when the locale is `ja`; every other locale downloads neither that stylesheet nor any font file, and its production CSS contains no Noto JP `@font-face` rule at all (0 bytes of growth), enforced by a postbuild check that fails the build otherwise. Nothing is requested from Google's servers at runtime. In every other locale, the switcher's "日本語" option carries `lang="ja"` and renders in the system Japanese font. On `/ja`, every text style uses the `--leading-*` values from `:root:lang(ja)`, body text uses `line-break: strict` (no small kana, ー, or closing bracket at a line start), and headings use `word-break: auto-phrase` where the browser supports it.
- **AC-12**: The plural forms test from spec 0047 passes with `ja`, and `packages/shared/src/pluralForms.test.ts` gains a `["ja", ["other"]]` row (required form `other` only). The i18next Node test returns the `_other` string for `ja` counts 0, 1, 2, and 5.
- **AC-13**: In `ja`, every message on the reviewed placeholder list from spec 0047 AC-12 reads naturally with the inserted name (Japanese nouns do not change form, so a sentence like `{names}が足りません` is allowed). The native reviewer checks the Japanese list.
- **AC-14**: Unit labels show `ml`, `cl`, `L`, `オンス` in `ja`. Batch labels and the drink idea limit copy have hand written Japanese values. All are approved by the native reviewer. Measures keep the dot decimal.
- **AC-15**: `translate-catalog --locale ja` translates the catalog with the pinned terms in `LOCALE_AI_TERMS.ja` (lime ライム, lemon レモン, the bar tools, and cocktail names in katakana with ・ between words, using the established Japanese name where one exists), and hash gating works per locale, so a second run translates nothing. Every recipe whose English ingredients include lime shows ライム and every lemon recipe shows レモン. After launch, the import job translates new recipes into `ja` too.
- **AC-16**: `propose-recipe-notes --locale ja` proposes Japanese notes for empty `ja` fields only, into `recipe-notes-proposals.ja.json`. The native reviewer reads every note before `apply-recipe-notes --locale ja` runs, and the apply writes only `ja` rows.
- **AC-17**: The web admin recipe form shows a Japanese notes section, and saving it updates only that recipe's `ja` row.
- **AC-18**: `generate-drink-idea` accepts `locale: "ja"` and writes the drink idea natively in polite Japanese with the pinned terms and Japanese punctuation (its copy of `normalizeJapaneseTypography`). Pantry verification still checks the English `source_name` only.
- **AC-19**: `user_preferences.locale` accepts `'ja'`, syncs, and follows the sign in merge rule from spec 0020 AC-16. Before launch, a stored `ja` preference counts as absent for detection and is left in place.
- **AC-20**: The `/ja` Open Graph share image is the English share image (English tagline, Fraunces), and its alt text and image metadata use the English tagline. Every other locale's image is unchanged.
- **AC-21**: On a real iOS device and a real Android device, both with English as the system language, with the app set to `ja`, Japanese renders with no clipped lines on the recipe screen, the pantry, and the account screen, the kanji 直, 骨, and 刃 show their Japanese forms (not the Chinese ones), and a rating count of 1 and of 2 both show the `_other` string.
- **AC-22**: All Japanese text written by AI or pinned in `LOCALE_AI_TERMS.ja` and the edge function instruction is stored in Unicode NFC, with no half width katakana and no full width digits.
- **AC-23**: Launch is one commit that adds `"ja"` to both `LAUNCHED_LOCALES` and `CATALOG_TRANSLATION_LOCALES`, made only after the catalog backfill, the notes apply, and the native review are signed off. It does not wait for features 69, 70, or 71 to pass `/check verify`. A mobile build ships with it, and the production sitemap and hreflang show `ja`.
- **AC-24**: Feature 60 lists Japanese among its store listing locales. The web launch does not wait on it.

## Decision

**Chosen option**: Option 1: The Hindi path, plus a CJK substring tier gated by script.

Japanese is added with the `simple` config and no locale specific SQL, gated behind `LAUNCHED_LOCALES`. One locale agnostic migration adds `search_fold` and `has_cjk` and a contains tier to `search_recipes` and `search_ingredients` that fires only for queries holding CJK characters. Web loads Noto Sans JP and Noto Serif JP only on `/ja`, from a self hosted stylesheet fetched from Google Fonts at build and linked by the layout only for `ja` (next/font would put their 248 slice rules, about 190 KB, into every locale's CSS), the share image maps `ja` to English, and a `normalizeJapaneseTypography` pass sets Japanese punctuation.

## Feature design

**Data model sketch**:

| Entity | Primary key | Fields | Foreign keys | Cardinality |
|---|---|---|---|---|
| `supported_locales` (new row) | `code` | `('ja', 'simple')` | none | one row |
| `recipe_translations`, `ingredient_translations`, `tag_translations`, `recipe_ingredient_translations` (new rows only) | unchanged | `locale = 'ja'` rows from the backfills; `name_search` set by the existing trigger with `simple` | `locale` → `supported_locales(code)`, unchanged | N:1, unchanged |
| `user_preferences.locale` | unchanged | now accepts `'ja'` through the existing foreign key | unchanged | unchanged |
| `public.search_fold(text) returns text` (new) | n/a | `language sql immutable parallel safe`, `set search_path = ''` | n/a | n/a |
| `public.has_cjk(text) returns boolean` (new) | n/a | `language sql immutable parallel safe`, `set search_path = ''` | n/a | n/a |

No table, column, extension, or index changes. Folding happens at query time; with about 430 recipes per locale, a sequential scan of the request locale's translation rows is trivial.

`search_fold(t)`, in order: `normalize(t, NFKC)` (half width ｼﾞﾝ becomes ジン, full width ＧＩＮ becomes GIN); `lower(...)`; `translate(...)` mapping hiragana U+3041 to U+3096 onto katakana U+30A1 to U+30F6, and ゝゞ onto ヽヾ; then `regexp_replace(..., '[\s・]', '', 'g')` to drop whitespace and the middle dot (U+30FB, which NFKC also produces from half width ･). `has_cjk(t)` is `t ~ '[぀-ヿ㐀-䶿一-鿿豈-﫿ｦ-ﾟᄀ-ᇿ㄰-㆏가-힯]'`, written with these `\u` escapes, never raw characters. The ranges are Hiragana and Katakana (3040 to 30FF), CJK Extension A (3400 to 4DBF), CJK Unified (4E00 to 9FFF), CJK Compatibility (F900 to FAFF), half width katakana (FF66 to FF9F), and Hangul Jamo, Compatibility Jamo, and Syllables (1100 to 11FF, 3130 to 318F, AC00 to D7AF). 々 (U+3005) and CJK Extension B and above (U+20000 and up) are left out on purpose: a query made only of them is vanishingly rare, and any query holding another kanji or kana still qualifies. Full width Latin (ＧＩＮ) is not CJK, so it never triggers the tier. Both helpers are immutable on this database (Postgres 17, `en_US.UTF-8`); a Unicode or collation upgrade that changed `normalize` or `lower` would need a rebuild only if they are ever indexed.

Out of scope: `search_bartender` and `search_recipes_by_ingredients` read only English names and aliases and take no locale, so they do not change.

**The CJK gate**: both functions compute it once in a CTE, `cjk_query as (select public.search_fold(query) as folded, public.has_cjk(query) and public.search_fold(query) <> '' as active)`. Every CJK condition below reads `(select active from cjk_query)` and `(select folded from cjk_query)`, so a query of only ・ or spaces (which passes `has_cjk` but folds to `''`, and `strpos(x, '')` is 1 for any `x`) never matches.

**`search_recipes` change**: a new CTE `name_cjk_matches` between `name_trgm_matches` and `ingredient_matches`, with `match_bucket = 1` (the same bucket as the English trigram tier) and `rank = (case when starts_with(public.search_fold(rt.name), folded) then 1.0 else 0.5 end)::real`. Its `where`: `active`, `rt.name is not null`, `strpos(public.search_fold(rt.name), folded) > 0`, not in `name_matches` and not in `name_trgm_matches` (a mixed query like B-52ショット can hit both tiers, and `union all` would list it twice), and the usual `deleted_at` and `status_filter` checks. The existing final order (`match_bucket`, `rank desc`, `fame_score desc nulls last`, `name`, `id`) then gives prefix first, then fame, inside bucket 1. In `ingredient_matches`, the existing parenthesized match group becomes `(query <% i.name or (it.name is not null and query <% it.name) or (active and it.name is not null and strpos(public.search_fold(it.name), folded) > 0))`, inside the same parentheses so every other filter still applies, and it also excludes ids in `name_cjk_matches`.

**`search_ingredients` change**: in `name_matches`, the parenthesized match group gains `or (active and it.name is not null and strpos(public.search_fold(it.name), folded) > 0)` inside its existing parentheses, so the `include_staples` filter still applies. Its rank becomes `greatest(<existing similarity expression>, (case when active and it.name is not null then case when starts_with(public.search_fold(it.name), folded) then 1.0 when strpos(public.search_fold(it.name), folded) > 0 then 0.5 else 0 end else 0 end)::real)`. For a query with no CJK character, `active` is false and the added rank is 0, so rows and order are unchanged (AC-6).

**Web surface**:
- **Japanese fonts do not go through `next/font`.** Google serves each CJK face as 124 unicode range slices; `next/font` writes every slice's `@font-face` rule into the CSS of the module that declares it, and the `[locale]` layout is shared, so declaring them there put about 190 KB (68 KB compressed) of rules into every locale's CSS (measured in build step 1, over the old 60 KB bound). Instead, the fonts ship as their own stylesheet, linked only on `/ja`. Measured on 2026-11-11: Google's CSS is about 115 KB per face; the slice files total about 5.5 MB (Noto Sans JP variable) and 4.0 MB (Noto Serif JP 600), of which a page downloads only the slices its characters need.
- `apps/web/scripts/script-fonts.config.mjs` (new, side effect free, only an exported constant): `SCRIPT_FONT_STYLESHEETS = [{ dir: "ja", families: ["Noto+Sans+JP:wght@100..900", "Noto+Serif+JP:wght@600"] }]`, one entry per script stylesheet. Both the fetch script and `display-font.test.ts` import it, so the test never triggers a download.
- `apps/web/scripts/fetch-script-fonts.mjs` (new, run with `tsx` like `generate-theme-css.mjs`, package script `fetch-script-fonts`). It imports the config above and `../src/lib/font-stylesheet.ts` by relative path with the `.ts` extension (no `@/` alias, which `tsx` does not resolve here), as `generate-theme-css.mjs` imports shared code. For each entry it makes one request, `https://fonts.googleapis.com/css2?family=<family 1>&family=<family 2>&display=swap` (families in config order; `display=swap` is what puts `font-display: swap` on every rule), with a pinned current desktop Chrome `User-Agent` (Google returns woff2 with `unicode-range` only to a modern browser UA). It passes the CSS to `rewriteFontStylesheet`, downloads every listed file (6 at a time, 3 retries each with a 1 s, 2 s, 4 s backoff) to `apps/web/public/fonts/<dir>/<family>/<version>/<file>.woff2`, and writes `fonts.css` and then a `stamp.json` last, so a partial run never leaves a stylesheet pointing at missing files. **Skip rule:** it skips an entry only when `fonts.css` exists, every URL in it has a file on disk, and `stamp.json` holds the same hash (SHA-256 of the entry's config plus the pinned user agent); otherwise it deletes `public/fonts/<dir>/` and fetches the entry again. `--force` always refetches. A clean checkout (Vercel) always fetches. **Failure:** any failure exits non zero, which fails the build (same as `next/font` today). If `process.argv.includes("--dev")`, it prints a warning and exits 0 instead, so offline dev still starts (see the fallback stacks in `globals.css`); other arguments are ignored. Wiring calls `tsx` directly so the flag never passes through pnpm's argument forwarding: `"prebuild": "pnpm run generate-theme && tsx ./scripts/fetch-script-fonts.mjs"`, `"predev": "pnpm run generate-theme && tsx ./scripts/fetch-script-fonts.mjs --dev"`.
- `turbo.json`: the `build` task's `outputs` gain `"public/fonts/**"`, and its `inputs` keep the default plus `scripts/script-fonts.config.mjs` (in the default already as a tracked file; stated so a narrowed `inputs` later keeps it). Without this, a Turborepo cache hit (local or Vercel remote cache) restores `.next/` but never recreates the gitignored `public/fonts/`, and `/ja` gets 404s for every font.
- `apps/web/src/lib/font-stylesheet.ts` (new, pure, with `font-stylesheet.test.ts` beside it): `rewriteFontStylesheet(css: string, publicDir: string): { ok: true; css: string; files: readonly { url: string; path: string }[] } | { ok: false; error: string }`. It strips comments, rewrites every `https://fonts.gstatic.com/s/<family>/<version>/<file>.woff2` URL to `/<publicDir>/<family>/<version>/<file>.woff2` (for example `/fonts/ja/notosansjp/v54/….woff2`), and returns each original URL with its local path. It takes a third argument, `minFacesPerFamily: number` (the script passes 100), and returns `ok: false` when the CSS has no `@font-face` rule, any family has fewer faces than that (so a change in Google's response shape, such as one unsliced file, fails loudly), a `src` URL outside `fonts.gstatic.com`, or a format other than woff2. It imports nothing from `next` or `@/` so the root vitest config (which already includes `apps/**/*.test.ts`) and `tsx` both load it. Tests cover a two face sample, comment stripping, the face minimum, a foreign host, and a non woff2 URL.
- `apps/web/.gitignore` gains `/public/fonts/`; the downloaded files are never committed.
- `apps/web/scripts/check-script-font-css.mjs` (new, package script `"postbuild"`): after `next build`, walks `.next/static/` by hand (a recursive `readdir`, since `fs.glob` needs Node 22 and the repo allows Node 20; with Turbopack the CSS lands in `.next/static/chunks/`) and fails with a non zero exit and the offending file names if: it finds zero `.css` files (so a changed output layout can't make the check pass vacuously); any of them has an `@font-face` rule naming a Noto JP family, `fonts.gstatic.com`, or `/fonts/ja/` (matched per rule on minified CSS with `/@font-face\{[^}]*(Noto[ _]+(Sans|Serif)[ _]+JP|fonts\.gstatic\.com|\/fonts\/ja\/)/i`, which also catches `next/font`'s `__Noto_Sans_JP_<hash>` renaming); `public/fonts/ja/fonts.css` is missing; or any URL in it has no file on disk. The `"Noto Sans JP"` and `"Noto Serif JP"` names in the global `:root:lang(ja)` variables are not `@font-face` rules and must pass. The matching lives in a pure exported function the script calls, with a test beside it: CSS holding the `:root:lang(ja)` block passes, CSS holding a Noto JP `@font-face` fails, and an empty file list fails. In build step 1, confirm in a Vercel build log that `prebuild` and `postbuild` both ran (pnpm runs pre and post scripts, as `prebuild` already relies on).
- `apps/web/src/lib/display-font.ts`: `DisplayFont` gains `"notoSerifJp"` with `DISPLAY_FONT_BY_LOCALE.ja = "notoSerifJp"`; `BodyScriptFont` gains `"notoSansJp"` with `BODY_SCRIPT_FONT_BY_LOCALE.ja = "notoSansJp"`. New `SCRIPT_FONT_STYLESHEET_BY_LOCALE: Record<Locale, string | null>` with `ja: "/fonts/ja/fonts.css"` and `null` for every other locale (a Record, so Korean and Chinese must each choose). Its test asserts `ja` maps to that path, every other locale to `null`, and every non null path is `/fonts/<dir>/fonts.css` for a `dir` in `SCRIPT_FONT_STYLESHEETS` (imported from `script-fonts.config.mjs`).
- `apps/web/src/app/[locale]/layout.tsx`: no `Noto_Sans_JP` or `Noto_Serif_JP` import. `DISPLAY_FONTS.notoSerifJp` is `{ variable: "" }` and `BODY_SCRIPT_FONT_CLASS.notoSansJp` is `""`, each with a comment that the `ja` stylesheet and the `:root:lang(ja)` block supply the font instead. When `SCRIPT_FONT_STYLESHEET_BY_LOCALE[locale]` is not null, `<head>` renders `<link rel="stylesheet" href={…} />` (plain, no `precedence` and no preload; the file is about 230 KB, roughly 70 KB compressed, and render blocking on `/ja` only, so headings never flash in the wrong family before the rules arrive). If `@next/next/no-css-tags` warns on it, add `// eslint-disable-next-line @next/next/no-css-tags` with a comment that this stylesheet is a static font file linked for `ja` only (spec 0050 AC-11). **Key invariants**:
- All 0045 to 0048 invariants hold. No SQL function body names `ja` or `simple`.
- The CJK tier changes nothing for a query without a CJK character, in any locale, and matches nothing for a query that folds to an empty string.
- No recipe appears twice in `search_recipes` output.
- `search_fold` and `has_cjk` are immutable and depend only on their input, so they stay safe to index later.
- `search_fold` is applied to both sides of every CJK comparison; never one side only.
- `ja` joins `LAUNCHED_LOCALES` and `CATALOG_TRANSLATION_LOCALES` in one commit, only after review sign off.
- The edge function's Japanese instruction duplicates `LOCALE_AI_TERMS.ja` by hand; a change to one changes the other in the same commit.
- `normalizeJapaneseTypography` is idempotent, its edge function copy matches it, and its output is NFC with no half width katakana.

**Security model**: no change. `supported_locales` stays read only for `anon` and `authenticated`. The recreated search functions keep their `security` setting, `search_path = ''`, and grants exactly; the migration restates `revoke ... from public` and each grant. The two helpers are pure, read no table, and get the same grants. No new PII. Compliance: Japanese is a language, not a market. This spec does not target Japan or change the age gate, so Japan's drinking age of 20 and the APPI (Japan's privacy law) are out of scope. Targeting Japan later needs its own legal review first.

**Configuration required**: no env vars or secrets. The web build now fetches from `fonts.googleapis.com` and `fonts.gstatic.com` in `prebuild` (as `next/font` already did inside `next build`), and `/fonts/` in `apps/web/public/` is a build output.

## Migration plan

**Strategy**: feature flagged (`LAUNCHED_LOCALES`), two additive migrations.
**Phases**: the `ja` row insert (step 1); the CJK search tier (step 2), which is live for every locale once applied but inert for any query without CJK characters; then backfills that only insert `ja` rows (steps 3 and 4).
**Rollback**: Japanese is invisible until step 6, so fix forward. For a full revert, the Japanese down SQL deletes the `ja` rows from the four translation tables, sets `user_preferences.locale` to null where it is `'ja'`, and deletes the `ja` row from `supported_locales`. The CJK search down SQL restores the previous function bodies and drops `search_fold` and `has_cjk`; no TS change depends on it.
**Risks**: the CJK migration replaces two live search functions used by every locale. A missed grant would break search for `anon` users everywhere, and a wrong condition could change Latin results; the before and after snapshot as `anon` catches both.

## Consequences

**Positive**:
- Japanese users get search that handles short queries, hiragana, half width input, and names with or without ・.
- Korean and Chinese inherit CJK search with no SQL change beyond their `supported_locales` row.
- Every other locale's search is provably unchanged.
- No new extension to run through the SQL editor.

**Negative / tradeoffs**:
- Contains matching has no real relevance ranking: prefix, then popularity. A long query with a typo finds nothing (no fuzzy tier for CJK).
- Kanji and kana spellings of the same word (梅酒 versus うめしゅ) don't match each other; only hiragana and katakana fold together.
- Search folds at query time with no index. Fine at about 430 recipes; past a few thousand rows per locale, add a stored folded column with a trigram index (the helpers are immutable, so that stays possible).
- Two more web fonts, and Noto Serif JP is a different typeface from Fraunces.
- The Japanese fonts sit outside `next/font`: a fetch script, a postbuild check, and a cache header to maintain, and no metric adjusted fallback face (a small layout shift on `/ja` while slices load, accepted). A Google Fonts outage fails the web build, as it already could through `next/font`.
- `/ja` pays one extra render blocking stylesheet (about 70 KB compressed) that other locales never load.
- `word-break: auto-phrase` works only in Chromium browsers; Safari and Firefox break headings anywhere.
- The `/ja` share image is in English. `/ja` URLs carry English words.
- Mobile depends on system fonts; an English set Android phone may show Chinese kanji forms, which the device check decides.
- Recipe text is machine translated and not reviewed. Learn and quizzes stay English under `/ja/`.
- Seven languages means more translation cost and one more string owed for every future feature.

**Neutral**:
- The default notes run's file gains a `ja` block at launch.
- Japanese uses the dot decimal and comma thousands like English, so feature 58 owes it nothing new.
